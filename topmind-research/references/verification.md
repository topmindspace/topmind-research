# 核验门（交付前强制执行）

collect 和 analyze 的任何产出交付前都要过本文件。未通过不交付；时间不够时，交付已通过的部分并写明未核验的条目。

## 一、来源分级

| 级别 | 定义 | 例子 |
|---|---|---|
| T0 | 一手来源 | 公司官网公告、官方 blog、论文原文、财报、system card、官方 GitHub 仓库 |
| T1 | 权威二手 | Reuters、AP、Bloomberg、官方通讯社 |
| T2 | 行业媒体 | 机器之心、量子位、新智元、TechCrunch、The Verge（以其注明的一手出处为准） |
| T3 | 传闻 / 自媒体 | X 爆料、匿名消息、「据悉」类，只作线索 |

## 二、按事实类型定核验强度

| 事实类型 | 最低要求 | 标注 |
|---|---|---|
| 公司自己的发布、定价、上线时间、人事任命 | 1 个 T0（官方原文） | 性能、排名、「首个 / 最强」类表述标「厂商口径」 |
| 第三方数字（融资额、估值、市场份额、榜单名次、用户数） | 2 个独立来源，至少 1 个 T0 或 T1 | 来源数字不一致时并列写出并说明各自出处 |
| 论文结论、实验数字 | 论文原文对应章节或表格（T0） | 二手解读只作线索；原文没写的写「原文未提及」 |
| 基准成绩 | 厂商自报 → 标「厂商口径」；第三方评测（如 Artificial Analysis、LMArena）→ 写明评测方与日期 | 不同口径（版本、测试集、日期）不并列硬比 |
| 传闻、爆料、匿名消息 | 不得作为结论，不进推荐语 | 标「传闻，未核实」 |

「独立来源」指不是互相转述的来源：两家媒体都引用同一篇官方公告，只算 1 个来源。

## 三、引用格式

1. 正文每个事实句末尾加 `[n]`，同一句多个来源写 `[1][3]`。
2. 文末「来源」表，每行一个来源：

   `[n] 标题 · 发布方 · 级别 · 发布 YYYY-MM-DD · 访问 YYYY-MM-DD · URL`

3. 发布日期查不到写「发布日期不详」；访问日期必须写。
4. 引用 T2 时，同一句同时给出它所引用的 T0（找得到的话）。
5. 编号从 1 连续递增，正文出现的编号必须都在来源表里，来源表里的编号必须在正文用到。可用 `scripts/check_citations.py <报告.md>` 检查。

## 四、引用支撑检查（交付前必做）

1. 列出报告中的关键句：所有数字、日期、人名、排名，以及结论段的每个判断。
2. 逐句打开对应 `[n]` 来源，核对原文是否支撑这句话（数字一致、主语一致、没有把「计划」写成「已发布」）。
3. 不一致：删除或改写该句；改写后仍无来源支撑的，按「无法核实」处理。
4. 在报告末尾「核验记录」写明：检查了几句、改了几句、删了几句、哪些链接打不开。

## 五、通用规则

1. **一手优先**：能找到 T0 就不用 T1/T2 转述。
2. **厂商口径**：公司自称的数据、排名、「首个 / 最强」类表述一律标「厂商口径」，不写成事实陈述。
3. **无法核实**：删掉，或明确标「未核实 / 传闻」，不写成肯定语气。
4. **时效**：每个来源写访问日期；研究结论写「截至 YYYY-MM-DD」。
5. **译名**：人名、产品名以官方为准；官方没有中文名时保留英文原名，不自造译名。存疑时只写英文。历史教训见 `references/errata.md`。
6. **数字**：金额、参数量、日期换算单位后复核一遍；百分比说明基数。

## 六、交付前自检清单

- [ ] 每个事实句都有 `[n]`，来源表编号连续、无悬空
- [ ] 每类事实达到第二节的最低要求
- [ ] 厂商口径已标注
- [ ] 未核实内容已删除或明确标注
- [ ] 引用支撑检查已做，核验记录已写
- [ ] 截至日期、访问日期已写
- [ ] 译名无自造

## 七、纠错

交付后发现事实错误：更正原报告并在文末「更正记录」写明日期和改动；列出已引用该报告的下游文件（专题笔记、事实表、已发快讯），在回执里提醒用户逐个确认是否同步修改。

## 八、隐私

1. 只收录公开信息源与公开人物的公开动态；不收录、不传播私人联系方式、住址等非公开个人信息。
2. 引用截图或转述时，隐藏无关人员的姓名、头像、联系方式。
3. 用户主动提供的私人资料只用于本次研究，不沉淀、不外传。
4. `config/sources.yaml` 中不得出现任何密钥、token、私有 API 地址（CI 的隐私扫描会检查）。
